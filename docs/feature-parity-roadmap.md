# Invest4Fun Feature Parity Roadmap

This document is the working map for bringing the new application to functional and visual parity with the reference product while keeping the new monorepo architecture.

The goal is not to copy files mechanically. Each feature is moved as a product capability, then implemented through the new boundaries:

- `apps/web`: React screens, local interaction state, routing and UI.
- `apps/api`: authenticated HTTP API and orchestration.
- `packages/contracts`: request and response schemas shared by web and API.
- `packages/database`: durable user, wallet, basket, order and activity data.
- `apps/worker`: asynchronous execution, polling, reconciliation and scheduled jobs.

## Current Status

### Working

- React application shell with routes for Feed, Ideas, Portfolio, Account and Activity.
- Privy login UI with email/social/passkey and wallet options.
- Server-side Privy bootstrap endpoint and root `.env.local` loading.
- Separate internal user identity and wallet records in the database model.
- Feed catalog with 13 curated Solana assets.
- CoinGecko spot market data with caching and curated fallback.
- CoinGecko historical charts with selectable periods.
- Swipe interaction for adding or skipping feed assets.
- Client basket state, basket rail and review modal flow.
- Draft basket review API with idempotency protection.
- Initial Ideas, Portfolio and Account screens.
- Dark theme and responsive application shell.

### Prototype Only

- Feed candidates are still a static curated catalog.
- `CLMT` is a placeholder asset without live market data.
- Asset icons, details and provider metadata are incomplete.
- Basket review creates a draft but does not fund or execute an order.
- Portfolio is not connected to live wallet balances.
- Ideas are not connected to the external catalog or historical performance data.
- Deposits, withdrawals, on-ramp providers and fiat transfers are not implemented.
- Jupiter, xStocks, gasless execution, webhooks and reconciliation are not implemented.

## Implementation Order

### Phase 1: Feed and Asset Data

**Purpose:** make the main browsing experience behave like the product and use trustworthy data.

Tasks:

- Replace the static feed list with a server-side feed pipeline.
- Add asset discovery, eligibility filtering, ranking and deterministic feed sessions.
- Add asset icon, CoinGecko metadata, market-cap rank, liquidity and source fields.
- Add asset details endpoint for the chart help panel.
- Keep market data requests server-side, cached and rate-limited.
- Add history coverage handling for new assets and unavailable periods.
- Add feed refresh/session expiry behavior.

Main files:

- `apps/api/src/catalog.ts`
- `apps/api/src/providers/`
- `apps/api/src/app.ts`
- `apps/web/src/screens/FeedScreen.tsx`
- `packages/contracts/src/index.ts`

Done when:

- Feed content is generated by the API, not hardcoded in the screen.
- Every displayed asset has a validated source, mint or explicit non-tradable status.
- Prices and charts show their actual update time and failure state.
- Feed behavior is deterministic for a session and refreshes intentionally.

### Phase 2: Ideas

**Purpose:** reproduce pre-built investment ideas as first-class products.

Tasks:

- Add the external idea catalog provider and a normalized internal idea model.
- Store idea holdings, weights, source, risk label and source URL.
- Add idea performance history and benchmark handling.
- Implement the same swipe, skip, details and add-to-basket behavior as Feed.
- Add idea snapshots so historical orders do not change when the catalog changes.

Main files:

- `apps/api/src/providers/`
- `apps/api/src/app.ts`
- `apps/web/src/screens/IdeasScreen.tsx`
- `packages/contracts/src/index.ts`
- `packages/database/migrations/`

Done when:

- A user can select either an individual asset or a complete idea.
- The basket stores the selected idea and its allocation snapshot.
- Idea charts and holdings are sourced from the API and have loading/error states.

### Phase 3: Basket and Review

**Purpose:** turn swipes into a reliable, reviewable order intent.

Tasks:

- Move basket draft state from browser-only state into authenticated persistence.
- Support asset and idea entries with amount, allocation and source snapshot.
- Add budget validation, minimum amount validation and duplicate handling.
- Add quote expiry, slippage and partial-execution messaging to review.
- Make review idempotent and safe to retry after refresh.
- Add explicit states: draft, awaiting funding, ready, executing, completed, failed.

Main files:

- `apps/web/src/state/basket-context.tsx`
- `apps/web/src/components/basket/BasketRail.tsx`
- `apps/api/src/app.ts`
- `packages/database/migrations/003_baskets_and_orders.sql`
- `packages/contracts/src/index.ts`

Done when:

- A basket survives page refresh and device changes.
- The review screen shows exactly what will be bought, for how much and through which route.
- A failed request can be retried without creating duplicate baskets or orders.

### Phase 4: Authentication, Users and Wallets

**Purpose:** make Privy an authentication and wallet provider, not the application user database.

Tasks:

- Verify Privy access tokens on the API.
- Upsert one internal user per Privy user ID.
- Persist linked identities and all embedded/external wallets.
- Handle wallet additions, wallet removal and active-wallet selection.
- Keep user-owned Invest4Fun wallet records separate from external wallets.
- Add account loading, bootstrap failure, sign-out and re-authentication states.

Main files:

- `apps/api/src/account-bootstrap.ts`
- `apps/api/src/app.ts`
- `apps/web/src/auth/auth-context.tsx`
- `apps/web/src/components/layout/WalletMenu.tsx`
- `packages/database/migrations/002_accounts_and_wallets.sql`

Done when:

- The same user can sign in through different Privy methods without duplicate internal users.
- All known wallets are displayed with role and provider.
- Refreshing the page restores the authenticated account from Privy and the API.

### Phase 5: Portfolio and On-Chain Positions

**Purpose:** show what the user actually owns in the Invest4Fun wallet.

Tasks:

- Add wallet balance provider for Solana positions.
- Normalize native SOL, SPL tokens and tokenized equity positions.
- Resolve balances to prices through the market-data layer.
- Aggregate repeated assets across Invest4Fun positions while preserving lot/order history.
- Add portfolio value, allocation, PnL, cost basis and activity history.
- Add stale-data and provider-unavailable states.

Main files:

- `apps/api/src/providers/`
- `apps/api/src/app.ts`
- `apps/web/src/screens/PortfolioScreen.tsx`
- `packages/contracts/src/index.ts`
- `apps/worker/src/index.ts`

Done when:

- Portfolio values are derived from persisted wallet positions and current prices.
- The same asset bought through multiple baskets is shown once in the aggregate view.
- The user can drill into the underlying lots and transactions.

### Phase 6: Funding and Withdrawals

**Purpose:** allow users to move money into and out of the Invest4Fun wallet.

Tasks:

- Add crypto deposit flow with destination wallet, network and confirmation status.
- Add country-specific on-ramp provider configuration.
- Store provider, country, quote/rate, fees, external transaction ID and status.
- Add bank/card funding states: initiated, pending, completed, failed, expired.
- Add withdrawal preparation, asset conversion and destination validation.
- Add KYC/AML, limits, fees and retention rules once product decisions are final.

Main files:

- `packages/database/migrations/`
- `apps/api/src/providers/`
- `apps/api/src/app.ts`
- `apps/web/src/screens/AccountScreen.tsx`
- `apps/worker/src/index.ts`

Done when:

- Every deposit and withdrawal has a durable provider record and status history.
- Users see clear pending/failure states and can safely retry where allowed.
- Provider callbacks are verified and idempotently reconciled.

### Phase 7: Execution

**Purpose:** execute a reviewed basket with the intended one-confirmation experience.

Tasks:

- Convert a reviewed basket into an execution intent.
- Build Jupiter swap routes for token purchases.
- Add xStocks execution path for supported tokenized equities.
- Decide and implement the canonical settlement asset.
- Add transaction size, account creation and route failure checks.
- Add gasless policy: eligible actions, sponsor limits, allowlist, retries and circuit breaker.
- Persist transaction signatures, quote data, route data and provider responses.

Main files:

- `apps/api/src/providers/jupiter.ts` equivalent provider module
- `apps/api/src/providers/xstocks.ts` equivalent provider module
- `apps/worker/src/index.ts`
- `packages/database/migrations/`
- `packages/contracts/src/index.ts`

Done when:

- The user reviews one basket and signs the intended action once where technically possible.
- Every execution has a traceable intent, quote, transaction and final status.
- Partial execution and retry behavior are explicit and safe.

### Phase 8: Activity and Reconciliation

**Purpose:** make asynchronous blockchain and provider operations trustworthy.

Tasks:

- Add activity records for deposits, swaps, purchases, withdrawals and failures.
- Add worker polling and webhook handlers.
- Reconcile provider status with on-chain signatures.
- Make reconciliation idempotent and assign a single owner for each operation.
- Add stuck-operation detection and circuit breakers.
- Connect Activity screen to real records.

Done when:

- A page refresh never loses an in-flight operation.
- API, worker, provider and chain statuses can be compared for every operation.
- An operator can identify and recover a stuck transaction.

### Phase 9: Production Readiness

**Purpose:** support real users and operational load.

Tasks:

- Add Redis or equivalent cache for shared market data and request coalescing.
- Add a queue for execution, provider callbacks and reconciliation jobs.
- Add database indexes, connection pooling and migration deployment.
- Add structured logs, metrics, error tracking and audit events.
- Add rate limits per user and provider-specific budgets.
- Add integration tests for Privy, CoinGecko, Jupiter, on-ramp and withdrawal flows.
- Split frontend chunks and audit the Privy bundle size.
- Deploy web, API, worker, database and secrets separately.

Done when:

- The system has a documented recovery path for provider, database and chain failures.
- Load tests cover the expected user volume and feed refresh patterns.
- No secret is required in the frontend bundle.

## What We Should Build Next

The next practical slice is **Phase 1 completion**:

1. Add asset icons and details to the API contract.
2. Replace the curated feed array with a provider-backed feed pipeline.
3. Add deterministic feed sessions and pagination.
4. Add the asset details panel to the chart help button.
5. Add focused API and screen tests.

After that, implement **Phase 3 Basket persistence** before starting real execution. This gives us a stable product workflow without prematurely coupling the UI to Jupiter or payment providers.

## Feature Status Rule

Each phase is complete only when all three layers exist:

1. The UI supports the user workflow.
2. The API validates and orchestrates it.
3. Durable state, tests and failure states exist where the workflow can outlive a page load.

Visual parity alone does not count as feature completion, and a backend endpoint without a usable screen does not count either.
